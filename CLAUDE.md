# Career-Ops -- AI Job Search Pipeline

AI-powered job search automation built on Claude Code: pipeline tracking, offer evaluation, CV generation, portal scanning, batch processing. The desktop app under `frontend/` is branded **starpath**.

The system is **designed to be made yours**. You (AI Agent) can edit the user's files. When the user asks to change archetypes, scoring, negotiation scripts, etc., do it directly. That's the whole point.

This file holds the rules. **Reference detail lives in [`docs/REPO-GUIDE.md`](docs/REPO-GUIDE.md)**: read the matching section before working in that area.

## Data Contract (CRITICAL)

Three layers; full list in `DATA_CONTRACT.md`.

- **Private root `private/`**: everything personal. CV, profile, trackers, reports, interview prep, outputs, JDs, batch state, chat sessions, caches built from the user's searches, personal docs (`private/docs/`) and the user's overrides (`private/overrides/`). It is gitignored by this repo and is **its own private git repo** (backup: `npm run backup`). The repo-root `user/ data/ reports/ interview-prep/ output/ jds/` (and a few `batch/` paths) are **links into it**, so every path in the modes works unchanged and whatever you write there lands in `private/`.
- **System layer** (public, generic): `modes/*`, `CLAUDE.md`, scripts, `templates/*`, the `batch/` prompt and runner, `frontend/*`, `docs/*`.
- **Demo layer** (public, fictional): `demo/`, generated by `npm run demo:build`; what the app shows when the user picks the demo.

**Where does a new file go?** Anything about the user, their search or their data goes under `private/` (or a linked path such as `data/`). A personal doc or note goes in `private/docs/`. Never in `docs/`, `modes/`, the repo root or `demo/`.

**Overrides instead of generalising.** To make a system file specific to this user (worked examples with their real schools, a mode tuned to their search, their CV template), write their version to `private/overrides/<same path>` (replaces the default) or `private/overrides/<path minus .md>.append.md` (added after it). Before reading any `modes/X.md`, `batch/batch-prompt.md` or `templates/*` file, check for both. Edit the public default only to change it for everyone, and keep it generic. Settings keep their homes: scoring weights, calibration and targets in `user/profile.yml`; archetypes, narrative and negotiation scripts in `user/_profile.md`; companies to scan in `user/portals.yml`.

### System Layer Hygiene

Public files stay generic. Before committing a change to `modes/*`, `scripts/*`, `templates/*`, `frontend/*`, `docs/*` or `CLAUDE.md`, ask: **would another user with a different background, country, school or dream companies get a wrong answer or surprising behavior from this?** If yes, it belongs in `private/` (data in `user/profile.yml`, wording in `private/overrides/`). Nothing personal has to be rewritten into fiction to exist; it just lives privately.

So: no worked examples naming the user's real schools, projects, proof points or dates; no hardcoded default lists (default to `[]`, fail closed) or per-company `if` branches (express them as data in `user/profile.yml`); no specific city/country/nationality as the canonical case. When a public file needs an example, make it fictional. Full checklist, including what legitimately stays (universal reference tables, test fixtures): `docs/REPO-GUIDE.md` § System layer hygiene.

### Public Repo — Personal Info Never Lands in Git

The GitHub repo is **public**. Every tracked file and every commit message is world-readable, and once something is committed it stays in history even if a later commit removes it.

- **Never commit personal information**: the user's contact details, the names of people they know, where they live, health, relationships or other private life, their schools, employers and projects, the companies and roles they applied to, scores, salaries or results from their own evaluations, and anything from their chats or memory. (The `package.json` author line is the user's own choice and the one exception.)
- **Copying counts as leaking.** Taking a real value from `private/` into a public doc example, comment, test fixture, prompt, design audit or commit message is a leak even when paraphrased. A savings figure from a real report or the role string of a real application must become invented values (fictional companies like "Nimbus Robotics", neutral cities like "Lyon"). If the real value is the point, it belongs in `private/overrides/` or `private/docs/` instead.
- **Personal files live only in `private/`.** `.gitignore` ignores it and every link path fail-closed; never add a `!` re-include.
- **The leak gate is automatic.** Versioned git hooks (`npm run hooks` once per clone) scan staged changes, commit messages and every push range against terms derived at run time from `private/` (CV, profile, tracker companies and roles, report names, network names, plus `private/leak-terms.txt` for anything it can't infer). **A blocked commit or push means fix the leak; never use `--no-verify`.** Also read `git diff --cached` yourself; `npm run leak-check` scans the whole tree. If a leak is in a commit that hasn't been pushed, fix it before pushing. If it was already pushed, tell the user: rewriting public history is their call.

## Profiles

When `private/profiles/` exists, several search profiles live under `private/profiles/<slug>/{user,data,reports}/` and exactly one is active (`private/profiles/active`). 18 canonical paths are symlinks into it: `user/profile.yml`, `user/portals.yml`, `user/_profile.md`, nine `data/` trackers and TSVs (`scouting.md`, `applications.md`, `pipeline.md`, `scan-history.tsv`, `score-history.tsv`, `dedup-index.tsv`, `discarded.tsv`, `report-summaries.tsv`, `filter-audit-state.json`), and the six `reports/` subdirs (`tier-1..4`, `positioning`, `briefs`). Everything else (`user/cv.md`, `data/network.md`, `data/outreach.md`, caches, `interview-prep/`, `batch/`) is shared.

- **Never write into an inactive profile.** Read and write the canonical paths; they resolve to the active profile.
- **Never replace a canonical symlink with a real file.** Plain writes follow symlinks and are fine; for write-temp-then-`rename`, resolve `fs.realpathSync(target)` first.
- **Write/Edit refuse file symlinks** (they do write through the directory links like `data/`). On "Refusing to write through symlink", edit the real target under `private/profiles/<active>/…` (`cat private/profiles/active`). That is the one case where writing a `profiles/` path is right, and only for the active profile.
- **Switching is CLI-only:** `npm run profile -- list` · `switch <slug> [--force]` · `create <slug> [--from <slug>] [--label "…"] [--switch]` · `init [<slug>]` · `eject`. Switch/init/eject refuse while unmerged eval TSVs, in-flight batch workers or unmerged JobSpy staging exist. `npm run doctor` validates either layout.

## First Run — Onboarding

**Before doing anything else, check that `user/cv.md`, `user/profile.yml`, `user/_profile.md` and `user/portals.yml` exist.** If any is missing, enter onboarding mode and run no evaluations, scans or other modes until they do. If `private/` itself is missing, run `npm run private -- init` first: it creates the private root, its git repo and the links, so everything onboarding writes lands in `private/`.

- **CV** → ask for a paste / LinkedIn URL / description; write clean markdown (Summary, Experience, Projects, Education, Skills).
- **profile.yml** → copy `config/profile.example.yml`; ask for name, email, location, target roles, salary range.
- **_profile.md** → create from the user's profile and goals (archetypes, narrative, negotiation scripts). Never overwritten by updates.
- **portals.yml** → target-role keywords for the scanner's Greenhouse/Ashby/Lever queries.
- **applications.md** → header `| # | Date | Company | Role | Score | Status | PDF | Deadline | Report | Notes |` (10 columns).

Then get to know the user (superpower, what excites or drains them, deal-breakers, best achievement, published work) and store it in `user/profile.yml`, `user/_profile.md` or `user/article-digest.md`. **After every evaluation, learn:** if the user corrects a score or adds context, update those same files. Once set up, offer recurring scans (`/loop`, `/schedule`, or cron).

## CV Source of Truth

`user/cv.md` is canonical; `user/article-digest.md` holds detailed proof points. **Never hardcode metrics**: read them from these files at evaluation time.

## Skill Modes

One evaluation mode (`scouting`); per-listing follow-ups (Tailor CV, Prep Application, Draft Application) are separate skills the user triggers. **The scoring model is `docs/scoring-v2.md`**: an eligibility gate (green / amber / red — red = Blocked, logged with its reason, no score), then **Want** and **Ease** (1–10); the Want × Ease grid gives the verdict (`go` · `stretch` · `growth` · `solid` · `thin` · `skip` · `blocked`) and the storage tier. No Overall; Priority (√(Want × Ease)) is a sort key only. Executable source of truth: `scripts/score-listing.mjs` (`scripts/lib/eligibility.mjs` + `scripts/lib/score-bands.mjs`). Mode files live in `modes/`.

## Ethical Use -- CRITICAL

**This system is designed for quality, not quantity.** Help the user find roles where there is a genuine match — not spam companies with mass applications.

- **NEVER submit an application without the user reviewing it first.** Fill forms, draft answers, generate PDFs — but always STOP before clicking Submit/Send/Apply. The user makes the final call.
- **Strongly discourage low-fit applications.** If the verdict is `skip` or `blocked`, explicitly recommend against applying (`thin` only with an explicit "only if your pipeline is thin" caveat; see `docs/scoring-v2.md` § 4). Only proceed if the user has a specific reason to override.
- **Quality over speed.** A well-targeted application to 5 companies beats a generic blast to 50.
- **Respect recruiters' time.** Every application a human reads costs someone's attention. Only send what's worth reading.

## Offer Verification -- MANDATORY

**NEVER trust WebSearch/WebFetch to verify if an offer is still active.** ALWAYS use Playwright:
1. `browser_navigate` to the URL
2. `browser_snapshot` to read content
3. Only footer/navbar without JD = closed. Title + description + Apply = active.

**Exception for batch workers (`claude -p`):** Playwright is not available in headless pipe mode. Use WebFetch as fallback and mark the report header with `**Verification:** unconfirmed (batch mode)`. The user can verify manually later.

## Pipeline Integrity

1. **NEVER edit applications.md to ADD entries**, and never create a second entry for an existing company+role. Write one TSV per evaluation to `batch/tracker-additions/` and let `node scripts/merge-tracker.mjs` merge it; **run it after each batch of evaluations**. You MAY edit existing rows' status/notes.
2. Scouting observations go to `data/scouting.md` with a Tier (`T1`–`T4`) instead of a status: write 12-column TSVs to `batch/scouting-additions/` (`modes/scouting.md` § Tracker Entry), run `node scripts/merge-scouting.mjs`, promote `go` hits (T1) with `node scripts/promote-to-applications.mjs <num>`.
3. Every report includes `**URL:**` in the header (after the Want · Ease / Eligibility / Verdict / Tier lines).
4. Health: `node scripts/verify-pipeline.mjs` · `normalize-statuses.mjs` · `dedup-tracker.mjs`. After a manual edit to scouting.md or applications.md, `node scripts/rebuild-dedup-index.mjs`.

### TSV Format for Tracker Additions

```
{num}\t{date}\t{company}\t{role}\t{status}\tW{want} E{ease}\t{pdf_emoji}\t{deadline}\t[{num}](reports/tier-{N}/{num}-{slug}-{date}.md)\t{note}
```

Status comes BEFORE score in the TSV (`merge-tracker.mjs` swaps them for `applications.md`). The tier `N` comes from `scripts/score-listing.mjs`, never by hand. Column details: `docs/REPO-GUIDE.md` § Tracker TSV.

### Canonical States

Source of truth: `templates/states.yml`. Statuses are `Evaluated` · `Applied` · `Responded` · `Interview` · `Offer` · `Rejected` · `Discarded` · `SKIP`. No bold, no dates, no extra text in the status cell (dates and notes have their own columns).

## Scoring Analytics

Every surface derived from `data/score-history.tsv` (`peer-rank`, `score-trend`, `calibration-advisor`, `positioning`'s trajectory) obeys `docs/scoring-statistical-design.md`: separate noise floors for Want (0.30) and Ease (0.35), per-surface minimum-information gates, and confidence tiers stated with each claim's `n`. Thresholds live in `scripts/lib/scoring-stats.mjs`; never restate them inline. A new score-derived analytic declares its gates in the doc first.

## Frontend Design System (MANDATORY)

**Before creating a UI component, changing styling, picking colors or adjusting layout in `frontend/`, read `DESIGN-meta.md`.** It is the single source of truth for palette, typography, spacing, component patterns and motion.

- Use the existing tokens: Tailwind classes from `frontend/tailwind.config.ts`, CSS variables / utilities from `frontend/src/app/globals.css`.
- **Colours are theme roles, never values.** The app has switchable themes (Settings › Appearance); every colour value lives in `frontend/src/app/themes.css`. Components use role classes (`bg-accent`, `text-text-3`, `bg-action`, `border-nav-line` …) or `themeColor()` / `tierColor()` for inline styles and SVG. A raw hex/rgb/oklch in a component fails `npm test` (`src/lib/colorLiterals.test.ts`); a theme missing a token or failing contrast fails `src/lib/themes.test.ts`. No role fits? Add one to every theme (DESIGN-meta.md § 2), never hard-code.
- **Don't introduce new colors, shadows, radii or type sizes** unless `DESIGN-meta.md` is updated in the same change.
- If a decision isn't covered by `DESIGN-meta.md`, raise it with the user before implementing.
- Markdown/TSV stay canonical: the app's SQLite cache is fully derived from them, and backend modes never read or write it. Chat never writes tracker files directly; it emits proposal fences (`modes/chat.md` § Proposals).

## Operational Feedback Loops

Two small logs (gitignored, shared across profiles):

- **Agent issue log** (`data/agent-log.tsv`): when you hit a schema mismatch, an unparseable data file, a URL pattern that keeps failing verification, or a rubric ambiguity, log it (`node scripts/agent-log.mjs log --category <schema|data|url|rubric|other> --subject "…" "…"`) instead of silently working around it. **Before maintenance or system work, check `node scripts/agent-log.mjs list --unresolved`** and `resolve` entries whose cause you fix.
- **Session handoff** (`data/session-handoff.md`): the data files hold facts; this holds the *thread*. End a session that leaves something unresolved with `npm run handoff -- write --slug <topic> --message "…"`. Read it (`npm run handoff -- read`) when the user refers back to earlier work or before a broad review.
- **Backup** (`npm run backup`): commits everything in `private/` and pushes it to the private remote. Run it at the end of a session that changed personal data; `npm run doctor` shows when the last backup was.

## Parallel Sessions & Branching

The user often runs several AI sessions on this repo at the same time, all pointed at the same checkout. To keep them from overwriting each other:

- **One feature, one branch.** Do every code or doc change on its own branch, preferably in its own worktree (`git worktree add .claude/worktrees/<topic> -b <type>/<topic>`), so two sessions never edit the same working tree. Don't build features directly on `main`.
- **Merge back when it's done.** Once tests/typecheck pass, bring the branch up to date with `main`, resolve any conflicts on the branch (never on `main`), merge it into `main`, then remove the worktree and branch.
- **Check before touching `main`.** Run `git status` first. Uncommitted files you didn't create belong to another session: don't commit, stash, revert, or overwrite them.
- **Data work stays in the main checkout.** `private/` and its links exist only there, so a worktree has no personal data. Evaluations, scans and tracker updates run in the main checkout, not on a feature branch.

## Agent Orchestration

When running as a top-tier model on multi-workstream tasks, default to orchestrating rather than typing: delegate spec'd, machine-verifiable work (tests/typecheck as the acceptance gate) to cheaper subagents, and spend own tokens on spec, judgment, review, and integration. Work inline when the task is small, single-surface, and already located — orchestration ceremony costs more than the work there.

Rules that are never optional:

1. **Strictly disjoint file surfaces per parallel agent.** Every dispatch names its complete owned-file list; two live agents never share a file. Sequence agents that need the same surface.
2. **Verify a spawn actually launched (and what it changed) before re-dispatching.** Never assume a lost agent did nothing.
3. **Single owner per change for shared contract surfaces:** `CLAUDE.md`/`AGENTS.md`/`docs/REPO-GUIDE.md` · the IPC contract (`frontend/electron/preload.ts` + `frontend/src/lib/ipc.ts` + the `frontend/electron/main.ts` handler registrations) · nav wiring (`frontend/src/store/nav.ts` + Sidebar/AppShell) · `batch/batch-prompt.md` + `modes/_shared.md` (parity-pinned by `scripts/batch-prompt-parity.test.mjs`) · root `package.json` · the profile symlink layout in `scripts/profile.mjs`. One agent (or the orchestrator) owns each of these per round; everyone else treats them as read-only.
4. **Concurrent sessions share this checkout** (see § Parallel Sessions & Branching). Do agent work in isolated git worktrees and merge to local main; never leave the main tree dirty with generated work, and check `git status` for another session's uncommitted files before merging anything that touches the same paths.
